# 文档编写原则

- 找到正确位置插入，不要简单追加
- 如果要写入的内容没有对应的文件，需要创建新的文档，需要经过用户的同意（但严禁为了避免请求用户而插入其他不合理位置）
- 同一内容只在最相关文档中出现，不要重复添加，其他文档保持引用
- 修复问题的场景，如果文档没有错误，不需要额外增量修改
- 增加新功能的场景，增量修改同时，合理精简已经没有参考价值的内容
- 直接阅读代码、脚本、模板等文件就能了解的内容，不要写入文档
- 如果在检查过程中发现有违反原则的问题，需要及时报告方案并请求用户同意，禁止忽略问题

## 文档边界

api：API contract（接口契约）。只写调用方可依赖的对外行为与约束（路径/方法、鉴权、请求/响应 schema、错误码、速率限制、幂等约束等）；不写后端内部流程/实现细节/部署与网关配置
data-dict：只包括数据库 schema 设计（表/字段/索引/约束）；不写业务流程与未来功能规划
plans：只包括方案文档（临时）。用于记录问题点、需求点、实施方案、实施结果，以及未实施能力/预留内容的跟踪
references：参考内容，不应被编辑和添加
spec：业务逻辑、交互与系统行为规范（以当前已落地实现为准）；未实施功能不得写入 spec
deployment/nginx：部署、运维、网关配置等内容放在 `deployment/*`、`nginx/*` 等目录，不写入 `docs/api/*`

## 方案文档原则

- plans 目录下的文档为方案文档
- 描述无歧义，不应该包含任何建议语气
- 非持久性文档，只作为本次任务指导，只包含问题点、需求点、实施方案、实施结果等内容。
- 不包含对于设计、定义、规范等持久化内容，如果此次任务中涉及到这类变更或需要参考这类内容，应该在项目文档中进行修改或新增，并在方案文档中引用

## 项目文档原则

- 非 `plans`、`references` 目录下文档为项目文档
- 以对未来提供指导和规范为原则，记录系统设计和规范，不应该包含过多实施描述、AI知晓的原则、标准等
- 必须始终对齐当前实现或即将实现内容，禁止保留变化历史，禁止保留多次修改痕迹
- 禁止包含建议、技术优势、设计理念、实施方案、问题描述、未来规划等
- 只说“是什么”，不说“不是什么”
