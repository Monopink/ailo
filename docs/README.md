# 文档编写原则

本文档定义项目文档的编写规范，确保文档模块化、职责单一、边界清晰，便于AI快速理解。

## 核心原则

### 1. 职责单一

每个文档只负责一个明确的主题：

- ✅ 好：`message/buffer.md` 只讲 AI 消息缓冲机制
- ❌ 差：一个文档同时讲缓冲、加密、路由

### 2. 避免重复定义

不同类型的文档有明确的职责边界：

- spec 文档需要表结构时 → 引用 data-dict 文档
- spec 文档需要接口定义时 → 引用 api 文档
- 只保留与当前主题直接相关的字段说明

### 3. 简洁直接

- 使用表格代替长段落
- 代码示例只保留关键部分
- 避免"技术优势"、"设计理念"等空话
- 中文为主，代码相关词使用原命名（如 `buffer`、`aggregate_state`）

### 4. 功能驱动

按功能场景组织内容，不按技术层次：

```markdown
<!-- ❌ 按技术层次 -->
## 数据层
## 服务层
## API层

<!-- ✅ 按功能场景 -->
## 用户发送消息
## AI 响应生成
## 消息发送失败处理
```

## 更新维护

### 何时更新文档

- 功能变更：修改相关 spec 文档
- 接口变更：修改 api 文档
- 表结构变更：修改 data-dict 文档
- 新增功能：评估是否需要新文档

### 更新原则

- 找到正确位置插入，不要简单追加
- 删除过时内容
- 更新相关文档的引用链接
- 保持文档间的一致性

## 检查清单

提交文档前检查：

- [ ] 职责单一，不包含无关内容
- [ ] 没有重复定义其他文档的内容
- [ ] 使用表格代替长段落
- [ ] 代码示例简洁且标注路径
- [ ] 开头说明职责和相关文档
- [ ] 删除了过时内容
- [ ] 更新了相关文档的链接
