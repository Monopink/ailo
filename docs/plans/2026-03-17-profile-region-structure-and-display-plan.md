# 2026-03-17 用户资料地区字段结构化与展示规范调整方案

## 问题点

- 小程序使用原生地区选择器到区县级，但资料地区的产品口径为市级，导致客户端存在“区县反推市级”的规则与名称清洗规则。
- 当前规则分散在多处实现，容易出现错误与展示不一致，且交互让用户选到区县但保存为市级，体验不一致。

## 需求点

- 地区字段主要用于资料展示，以及作为 AI 了解用户的背景信息。
- 中国大陆：选择到市级（地级市/地区/自治州/盟/直辖市等）；当行政层级不存在地级层时，保存用户在市级选择器层级能选择到的最细单位。
- 港澳台：由于业务调整，当前版本暂不支持选择与写入（仅保留中国大陆）。
- 地区展示不包含“省”“市”“自治区”“自治州”等行政区划后缀。
- 暂不提供地区隐私开关。
- 未来 App 端需要复用同一套地区存储结构。

## 方案定义

### 交互与提交

- 客户端选择流程为：（中国大陆）省 -> 市。
- 小程序端使用 `picker mode="region"` 且层级为市级，提交时同时上送 `event.detail.code` 与选择得到的省名、市名原文；`region` 由后端生成。
- App 端使用后端下发的省/市数据做级联选择，写入同一套结构化字段。

### 存储结构

`profiles` 表新增字段（与现有 `region` 并存）：

- `region_country_code`：国家/地区代码（ISO 3166-1 alpha-2），当前仅使用 CN。
- `region_cn_city_code`：中国大陆市级行政区划代码（6 位字符串），仅当 `region_country_code=CN` 时写入。

`region` 字段作为展示快照，展示规范见 `docs/spec/client/base/profile-and-settings.md`。

### 接口影响

- `PUT /api/v1/user/profile`：支持 `region_country_code`、`region_cn_city_code`、`region_province_name`、`region_city_name` 写入；`region` 由后端生成。
- `GET /api/v1/user/profile`、`GET /api/v1/contacts`、`GET /api/v1/discovery/*` 等返回资料的接口：仅返回 `region` 展示快照。

### 需要移除的规则

- “省直辖县级行政区划/自治区直辖县级行政区划/县”等名称特判反推规则。
- 地区展示采用统一清洗规则生成，不允许在多处实现分散规则。

## 实施步骤

1. 更新文档：地区展示规范、资料字段规范、API 文档、数据字典（本次阶段）。
2. 数据库：新增 `profiles` 表字段，同步初始化脚本与数据字典；补充迁移脚本。
3. 后端：更新 Profile 模型与相关 Schema；更新资料写入校验；补充日志记录字段。
4. 小程序：改为市级选择器；写入结构化字段与省市名称原文；展示使用 `region` 快照。
5. App：实现国家/地区与省市级联选择；写入同一套结构化字段与省市名称原文。

## 验收标准

- 小程序资料地区交互只出现国家/地区与省市级联选择，不出现区县级选择。
- `region` 展示内容符合规范，且 contacts/discovery 等所有资料展示一致。
- 当 `region_country_code=CN` 时，`region_cn_city_code` 必须存在。
- 代码侧不再存在地区名称特判与后缀清洗逻辑。
