# 2026-05-15 消息服务 WS 域名与连接稳定性整改计划

## 文档状态

- 状态：已实施
- 创建日期：`2026-05-15`
- 最后更新：`2026-05-15`
- 适用范围：后端 `ws-session` 下发链路、小程序 WebSocket 连接状态机、消息发送恢复路径、消息相关 spec/api 文档

## 目标

1. 消除 `createSocketTask:fail url not in domain list` 导致的长期不可发送状态。
2. 保持消息服务初始化非阻塞，同时确保发送路径在连接异常时具备确定性恢复行为。
3. 消除错误域名高频重连风暴，提供低频自动恢复探测能力。
4. 保持健康接口口径不变。

## 已确认决策

1. `ws-session.session.server_url` 仅使用 `system_configs.api_base_url` 作为唯一来源。
2. 移除 `request.base_url` 回退路径。
3. `system_configs.api_base_url` 缺失或非法时，`POST /api/v1/messages/ws-session` 返回 5xx。
4. 小程序命中 `url not in domain list` 时：
   - 立即强制执行一次会话刷新（`conversationStore.refresh()`）；
   - 刷新后仍失败则进入配置错误态，并停止高频重连；
   - 启用低频自动探测刷新，周期 `60s`，附加轻微随机抖动。
5. 当前阶段采用单实例运行约束，仅通过文档与部署说明固化，不增加启动时自检逻辑。
6. 后端健康口径保持现态，不调整 `/health` 合同。
7. 本次任务同步更新相关文档，保证文档与实现一致。

## 问题点（现态）

1. `ws-session` 返回地址来源与请求 Host 绑定，地址稳定性依赖入口链路形态。
2. 客户端连接失败后存在坏地址复用路径，导致持续发送失败。
3. 域名白名单错误场景缺少专用状态机分支，重连行为缺少节流边界。
4. 会话缓存缺少“配置错误态”语义，故障可观察性与恢复策略耦合在通用重连流程中。

## 实施范围

### 后端

1. 调整 `POST /api/v1/messages/ws-session` 的 `server_url` 生成逻辑。
2. 新增 `api_base_url` 读取与合法性校验路径（空值、协议、尾斜杠规范化）。
3. 为 `ws-session` 地址配置异常补充结构化日志与错误响应。

### 小程序

1. 新增 `url not in domain list` 专用错误分类。
2. 新增“配置错误态”连接状态分支与事件上报。
3. 在该错误分支执行“立即强制刷新一次 + 低频自动探测刷新”。
4. 调整重连调度器，配置错误态不参与高频指数退避重连。
5. 发送入口在配置错误态下返回确定性失败原因，维持现有失败态消息展示语义。

### 文档

1. 更新 `docs/api/messages-ws-session.md`。
2. 更新 `docs/spec/message/websocket.md`。
3. 更新消息稳定性相关计划文档引用关系。
4. 增补单实例运行约束说明到部署文档（仅文档约束）。

## 实施任务

### 1. 后端 `ws-session` 地址下发收敛

1. 在系统配置读取链路中获取 `api_base_url`。
2. 实施统一规范化函数：
   - 去尾部 `/`
   - 要求 `https://` 协议
   - 非空校验
3. `ws-session` 响应中的 `session.server_url` 固定返回规范化结果。
4. 配置无效时返回 5xx，并记录错误码、配置键、request_id。

### 2. 客户端配置错误态状态机

1. 在 WS 连接错误解析中识别 `url not in domain list`。
2. 增加连接内部状态 `config_error`（内部态），并映射到现有 UI 可消费状态。
3. 进入 `config_error` 时执行：
   - 立即 `conversationStore.refresh()`；
   - 若刷新后首次重连成功，清理错误态并恢复正常调度；
   - 若刷新后仍失败，保持 `config_error` 并启动低频探测定时器。
4. 低频探测规则：
   - 周期 `60s`；
   - 抖动 `±10%`；
   - 单次探测包含一次刷新与一次连接尝试；
   - 成功后立即停止探测定时器并恢复正常连接状态机。

### 3. 发送路径与错误反馈收敛

1. `sendMessage` 在 `config_error` 场景返回稳定错误码（用于前端失败态与日志聚合）。
2. 运行态上报新增字段：`recovery_mode`、`probe_interval_ms`、`probe_attempt`。
3. 保持现有消息失败展示与重试入口，不改变页面交互合同。

### 4. 文档与部署约束同步

1. 在 API 文档明确 `server_url` 来源与配置要求。
2. 在 spec 文档明确域名错误场景下的客户端恢复行为。
3. 在部署文档明确当前运行约束：消息服务采用单实例部署。

## 验收标准

1. 当 `api_base_url` 配置有效且域名在微信 WebSocket 合法域名列表内时，首次进入可稳定建连并发送消息。
2. 当 `api_base_url` 指向非白名单域名时：
   - 客户端触发一次立即刷新；
   - 随后进入低频探测模式；
   - 无高频重连风暴；
   - 消息发送返回确定性失败原因。
3. 配置修复后，无需重启小程序，低频探测可自动恢复连接与发送能力。
4. `/health` 接口响应合同保持不变。
5. `docs/api/*` 与 `docs/spec/*` 的消息相关描述与实现行为一致。

## 验证计划

1. 后端验证：
   - `api_base_url` 合法值：`ws-session` 返回固定 `server_url`。
   - `api_base_url` 非法值：`ws-session` 返回 5xx。
2. 小程序验证：
   - 构造白名单外域名，验证一次立即刷新与低频探测调度。
   - 修复配置后验证自动恢复，无需重启。
3. 回归验证：
   - 发送/接收/离线拉取/ACK 基本链路通过。
   - 现有页面“失败态消息 + 重试入口”行为一致。
