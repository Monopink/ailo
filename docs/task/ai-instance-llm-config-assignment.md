# AI Instance LLM Config Assignment

## Current Capability

- 模板在创建实例时提供默认的 `llm_config_id`，之后实例与模板完全解耦，彼此的配置调整互不影响。
- 实例运行时的配置解析遵循两级优先级：实例自身的 `llm_config_id`（若有效）优先，其次退回到系统主配置。
- `request_params` 仍用于实例级别的运行参数覆盖，可在不改变 `llm_config_id` 的情况下微调温度、最大 token 等值。
- 后台管理界面已支持在模板和实例详情中查看与编辑 `llm_config_id`，便于运营团队显式指派供应商配置。

## 运行规则

1. **初始化阶段**
   - 模板、实例表均已具备 `llm_config_id` 字段及针对非空值的局部索引。
   - 实例创建流程会在落库时快照模板的配置编号；如果模板未指定，则实例保持空值。

2. **对话调度阶段**
   - 测试场景（显式传入 `config_name`）仍允许绕过实例配置以便验证不同供应商。
   - 生产场景下统一调用实例级解析逻辑：先尝试实例存储的配置，若不可用则直接回退到系统主配置，并记录日志链路。
   - `request_overrides` 仅用于测试或调试，不会被持久化。

3. **参数覆盖顺序**
   - 实时函数调用入参 > `instance.request_params` > 所解析出的 LLM 配置默认值。
   - 该顺序必须在任何新增入口保持一致，避免出现参数来源不透明的情况。

## 待验证事项

1. **运行期观测**
   - 持续跟踪实例级配置的命中率与回退次数，确保异常配置能够及时被监控报警。
   - 针对配置下线或禁用的情况，需要在运营流程中明确指派新的 `llm_config_id`。

2. **数据一致性检查**
   - 周期性抽查模板与实例的 `llm_config_id`，确认导数脚本或手工操作不会写入无效编号。
   - 当管理员在实例详情页更新 `llm_config_id` 时，需验证其生效路径（聊天、测试页）均能读取到更新值。

3. **功能回归**
   - 对应的 API、后台操作、实例创建流程需要保持一致的解析逻辑，后续改动必须包含联动测试。
   - 一旦检测到异常回退（频繁落到系统主配置），需排查实例配置是否被接口或任务意外清空。

## 后续改进方向

- 建立「配置健康状态」面板，区分实例直接命中的配置与被动回退的比例，为运营提供可视化支持。
- 对接审计日志，记录何时由哪个管理员调整了模板或实例的 `llm_config_id`，便于追踪问题。
- 评估是否需要在实例导入或批量操作工具中加入配置校验，避免一次性写入大量失效编号。
